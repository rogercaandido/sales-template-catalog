# Research: Report Admin Dashboard Feature

**Feature**: `/reportadminx` - Marketing Analytics Report Viewer
**Date**: 2026-01-13
**Context**: Extension to Template Catalog project for displaying marketing team analytics reports

## Overview

The marketing team needs a way to upload, organize, and view HTML-based analytics reports (e.g., lead analysis, conversion metrics). The dashboard will provide period-based filtering and full report viewing capability.

## Technical Decisions

### Decision 1: Architecture Pattern

**Chosen**: Multi-page application with routing (client-side)

**Rationale**:
- The user explicitly requested a separate page at `/reportadminx`
- Reports are full HTML documents that need dedicated viewing space
- Maintains separation between template catalog (main page) and report dashboard (admin page)
- Allows independent styling and UX for report management vs template browsing

**Alternatives Considered**:
1. **Single-page with modal overlay** - Rejected: Reports are too complex to fit in modals
2. **Separate standalone HTML file** - Rejected: Doesn't scale, duplicates styles and navigation
3. **iframe-based embedding** - Considered: May use for report rendering to isolate report styles

**Implementation Approach**:
- Use hash-based routing (`#/reportadminx`) for simplicity (no server config needed)
- Main index.html serves as router
- Report dashboard renders as dedicated view
- Maintains developer dark mode aesthetic from template catalog

---

### Decision 2: Report Storage Strategy

**Chosen**: Static HTML files in `/reports/` directory with JSON metadata index

**Rationale**:
- Reports are static HTML generated by marketing team
- No database required (keeps deployment simple)
- Git-trackable (version history for free)
- Zero backend infrastructure needed
- Can deploy anywhere (Netlify, Vercel, GitHub Pages)

**Alternatives Considered**:
1. **Database storage (Firebase, Supabase)** - Rejected: Adds complexity, cost, authentication overhead
2. **LocalStorage** - Rejected: Can't share reports across team members
3. **External CMS** - Rejected: Over-engineering for static HTML files

**Structure**:
```
reports/
├── index.json              # Metadata: {id, title, period, dateCreated, fileName}
└── leads-2026-01-12.html   # Individual report HTML files
```

**Metadata Schema** (reports/index.json):
```json
{
  "reports": [
    {
      "id": "rpt-001",
      "title": "Relatório Estratégico de Leads",
      "period": {
        "start": "2025-12-05",
        "end": "2026-01-12"
      },
      "dateCreated": "2026-01-12",
      "fileName": "leads-2026-01-12.html",
      "tags": ["leads", "meta-ads", "educação-cosmética"]
    }
  ]
}
```

---

### Decision 3: Report Rendering Method

**Chosen**: iframe with sandbox attributes for security

**Rationale**:
- Reports use arbitrary HTML/CSS/inline styles (like the example provided)
- iframe provides style isolation (report styles won't leak into dashboard)
- Sandbox attributes prevent malicious scripts if reports come from untrusted sources
- Can still display full interactive content (tables, hover effects)

**Security Configuration**:
```html
<iframe
  sandbox="allow-same-origin"
  src="/reports/leads-2026-01-12.html"
  style="width: 100%; height: 100vh; border: none;"
></iframe>
```

**Alternatives Considered**:
1. **Direct HTML injection** - Rejected: Style conflicts, potential XSS if reports are user-generated
2. **Shadow DOM** - Rejected: Limited browser support, complex implementation
3. **Convert to markdown** - Rejected: Loses report styling and interactivity

---

### Decision 4: Period Filtering UI

**Chosen**: Date range dropdown with preset periods (Last 7 days, Last 30 days, Last quarter, All time, Custom)

**Rationale**:
- Marketing teams think in time periods (weekly, monthly, quarterly)
- Preset options reduce friction (most common use case)
- Custom option for ad-hoc queries
- Matches standard analytics tool UX patterns

**Filter Logic**:
```javascript
const filterReports = (reports, period) => {
  const now = new Date();
  const filters = {
    'last-7-days': (r) => daysSince(r.dateCreated) <= 7,
    'last-30-days': (r) => daysSince(r.dateCreated) <= 30,
    'last-quarter': (r) => daysSince(r.dateCreated) <= 90,
    'all-time': (r) => true,
    'custom': (r) => isInRange(r.period, customStart, customEnd)
  };
  return reports.filter(filters[period]);
};
```

**Alternatives Considered**:
1. **Calendar widget** - Rejected: Too heavy for simple filtering
2. **Text search only** - Rejected: Doesn't match mental model of "period-based reports"
3. **Year/Month dropdowns** - Considered: May add if preset options prove insufficient

---

### Decision 5: Report Upload Mechanism

**Chosen**: Manual file addition via Git (no upload UI in MVP)

**Rationale**:
- Marketing team likely has technical support (can do Git operations)
- Avoids complex file upload, validation, and storage logic
- Fits existing Git-based workflow (entire project is version controlled)
- Upload UI can be added later if needed (Phase 2 feature)

**Workflow**:
1. Marketing exports report HTML from their analysis tool
2. Add HTML file to `/reports/` directory
3. Update `reports/index.json` with metadata entry
4. Git commit + push
5. Auto-deploy (if using Netlify/Vercel)

**Alternatives Considered**:
1. **Drag-and-drop upload UI** - Deferred: Requires backend or client-side file API
2. **Google Drive integration** - Rejected: Adds external dependency
3. **Email-to-report** - Rejected: Over-engineering

---

### Decision 6: UI Layout and Navigation

**Chosen**: Two-column layout with report list (left) and preview pane (right)

**Rationale**:
- Matches standard email client / file explorer UX pattern (familiar)
- Report list shows metadata at a glance (title, date, tags)
- Preview pane shows selected report in iframe
- Responsive: Stacks to single column on mobile (<768px)

**Layout Sketch**:
```
┌─────────────────────────────────────────────┐
│  Header: Report Dashboard                   │
├─────────────┬───────────────────────────────┤
│             │                               │
│  Filters    │                               │
│  (period)   │                               │
│             │                               │
│  Report     │       Report Preview          │
│  List       │       (iframe)                │
│  (metadata) │                               │
│             │                               │
│             │                               │
└─────────────┴───────────────────────────────┘
```

**Alternatives Considered**:
1. **Full-screen report view with back button** - Rejected: Loses context, harder to compare reports
2. **Grid of report cards** - Rejected: Reports need full viewport to be readable
3. **Tab interface** - Rejected: Limits to viewing one report at a time

### Decision 8: Report Metadata Tags

**Chosen**: Simple tag array with visual badges (no filtering by tag in MVP)

**Rationale**:

## Best Practices Applied

### Performance
- **Lazy loading**: Reports only load when selected (not all at once)
- **Iframe sandboxing**: Prevents expensive scripts in reports from blocking main UI
- **Minimal JavaScript**: Filtering and selection logic only

### Accessibility
- **Keyboard navigation**: Arrow keys to navigate report list, Enter to select
- **Screen reader support**: Proper ARIA labels for report list items
- **Focus management**: Clear focus indicators, logical tab order

### Maintainability
- **Data-driven rendering**: Report list renders from JSON (easy to update)
- **Separation of concerns**: Report content (HTML) separate from dashboard logic
- **Consistent naming**: `reports/report-{type}-{date}.html` convention
